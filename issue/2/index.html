nginx2root (CVE-2026-123007 и ещё четыре): пять ошибок памяти в nginx, найденных с помощью ИИ

--rubric "Уязвимости, найденные ИИ" --tag nginx rce

Уязвимости: nginx2root (CVE-2026-123007 и ещё четыре)

18 ноября nginx выпустил версии 1.30.7 и 1.31.9 и закрыл пять ошибок памяти, которые исследователи из Xint назвали nginx2root (nginx.org). Все пять — в рабочем процессе nginx (worker). По данным F5, удалённый атакующий без аутентификации может уронить этот процесс или повредить его память, а если ASLR отключён или обойдён — выполнить свой код (запись CVE). Каждая уязвимость срабатывает в своей конфигурации. Главная — CVE-2026-123007: она касается любой конфигурации с HTTP/2.

Что сломано

CVEГдеЧто происходитУязвимые версии
CVE-2026-123007HTTP/2Окно flow control выходит за допустимую границу, и nginx пишет за пределы буфера в heap1.9.5–1.31.8
CVE-2026-123633HTTP/2 при проксировании на бэкендUse-after-free, когда у процесса заканчиваются worker_connections1.19.7–1.31.8
CVE-2026-123634resolverUse-after-free, если в proxy_pass есть переменные, а SSI или mirror делает подзапрос к тому же имени0.6.18–1.31.8
CVE-2026-121810HTTP/3Use-after-free. По словам F5, эксплуатация зависит от условий, которые атакующий не контролирует1.25.0–1.31.8
CVE-2026-113425почтовый проксиUse-after-free0.5.33–1.31.8

Уязвимые версии — по nginx.org, описания — по записям CVE от F5. Те же релизы закрывают ещё три уязвимости, которые в nginx2root не входят, список — на nginx.org.

Кого касается

nginx Open Source из диапазонов в таблице, если включена соответствующая функция. Если в конфигурации есть http2 в listen или http2 on;, вас касается CVE-2026-123007. NGINX Plus тоже затронут: исправленные сборки — в бюллетенях F5 (K000163926 и ссылки из записей CVE).

Дистрибутивы переносят исправления в свои версии. Например, на 21 ноября Ubuntu выпустила:

UbuntuИсправленный пакет nginx
22.041.18.0-6ubuntu14.23
24.041.24.0-2ubuntu7.20
26.041.28.3-2ubuntu1.13
26.101.30.4-7ubuntu1.2

Поэтому по одному номеру версии nginx не понять, исправлен ли он: 1.28.3 в Ubuntu 26.04 исправлен, если номер сборки пакета — 1.28.3-2ubuntu1.13 или выше.

По оценке Xint, на 10 ноября из 11,94 млн хостов nginx с видимой в Shodan версией 98,9% попадали в уязвимый диапазон. Xint оговаривает, что это подсчёт по строке версии, а не проверка уязвимости.

Насколько опасно

F5 оценивает каждую из пяти уязвимостей в 8.1 по CVSS 3.1 с высокой сложностью атаки (AC:H) и в 9.2 по CVSS 4.0 (записи CVE). На 18 ноября CISA по своей шкале SSVC оценила, что эксплуатации нет и автоматизировать атаку нельзя. На 21 ноября ни одной из пяти нет в каталоге KEV (NVD).

Исследователи заявляют больше, чем F5:

  • Wiz пишет, что выполнила код через CVE-2026-123007 на nginx, который раздаёт обычные статические файлы по HTTP/2 поверх TLS, без бэкенда и сторонних модулей. Для этого понадобился обход ASLR. Эксплойты Wiz не публикует.
  • Xint пишет, что получила выполнение команд с правами рабочего процесса nginx, а в связке с отдельной уязвимостью ядра Linux — выход из Docker-контейнера и root на хосте.

Моя оценка: для nginx с HTTP/2, доступного из интернета, риск высокий, для конфигураций только с HTTP/1.1 — средний. Атака сложная и требует обхода ASLR, но, по словам Wiz, для неё хватает nginx, который просто раздаёт статику по HTTP/2.

Почему это история про ИИ

За CVE-2026-123007 F5 благодарит сразу четыре команды: Rapid7, Wiz, Xint и Ikotas Labs. Ikotas, по записи CVE, нашла ошибку с помощью модели GPT-6 Astra. По словам Xint, первую уязвимость нашёл исследователь, а остальные четыре через несколько дней — полностью автоматический сканер Xint. Wiz пишет, что обе ошибки HTTP/2 нашла её система Wiz Atlas, а последствия проверяли с помощью Gemini 4 Carbon и ChatGPT 5.6 Sol.

Для меня главное здесь — четыре независимые находки одной ошибки, которая живёт в nginx с версии 1.9.5. Когда ИИ-инструменты разных команд прогоняют один и тот же популярный код, они находят одни и те же ошибки почти одновременно. Значит, нельзя рассчитывать, что об уязвимости знает только тот, кто сообщил о ней вендору.

Что сделать

  1. Проверьте версию. На хосте и в каждом образе с nginx:
    nginx -v
dpkg -l nginx | awk '/^ii/{print $3}'          # номер сборки пакета в Debian и Ubuntu
  2. Посмотрите, какие функции включены. От этого зависит, какие из пяти уязвимостей вас касаются:
    nginx -T 2>/dev/null | grep -nE 'http2|quic|http3|resolver|mirror|ssi on|^\s*mail'
  3. Обновитесь до 1.30.7 или 1.31.9 либо до исправленного пакета своего дистрибутива. Для NGINX Plus — сборки из бюллетеней F5.
  4. Перезапустите nginx. reload перечитывает конфигурацию, но оставляет в памяти старый бинарник:
    sudo nginx -t && sudo systemctl restart nginx
ps -o lstart= -p "$(cat /run/nginx.pid)"       # мастер-процесс должен быть запущен позже обновления пакета
grep ' nginx' /var/log/dpkg.log                # когда пакет поставили или обновили
    Дату обновления смотрите в журнале dpkg, а не по файлу /usr/sbin/nginx: dpkg сохраняет у файлов время из пакета, то есть время сборки. Я сам на этом ошибся в первой версии разбора. Если у вас автообновления, проверьте, что после них nginx перезапускался.
  5. Если обновиться сегодня нельзя, Xint советует отключить HTTP/2: в nginx 1.25.1 и новее поставьте http2 off; в каждом блоке server и уберите http2 из listen. Это закрывает только CVE-2026-123007 и CVE-2026-123633. Для остальных отключите то, чем не пользуетесь: HTTP/3, почтовый прокси, переменные в proxy_pass вместе с SSI или mirror.
