Java4Shell (CVE-2026-114938): Calif нашла уязвимость в OpenJDK с помощью ИИ-агента за час

--rubric "Уязвимости, найденные ИИ" --tag openjdk rce

Уязвимость: Java4Shell (CVE-2026-114938)

17 ноября Oracle и OpenJDK закрыли CVE-2026-114938 — heap buffer overflow в Base64-декодере OpenJDK (oss-security). Исследователи из Calif назвали уязвимость Java4Shell и, по их словам, нашли её с помощью ИИ-агента. Чтобы ускорить декодирование Base64, OpenJDK использует инструкции AVX-512 VBMI на процессорах x86-64, которые их поддерживают (Calif). Ошибка — именно в этом коде, поэтому уязвим любой такой процессор. ARM64 не затронут. По данным Calif, удалённый атакующий без учётной записи может прочитать память процесса и выполнить свой код.

Что сломано

Если подать JVM специально подобранную строку в Base64, ускоренный декодер запишет данные за пределы выделенного буфера в heap — области памяти, где JVM хранит объекты (разбор Calif). NVD относит ошибку к классу CWE-122: heap-based buffer overflow.

Для атаки нужно, чтобы приложение декодировало Base64 из входящих данных. Какие пути в вашем коде и библиотеках ведут в этот декодер, источники не перечисляют, поэтому надёжнее считать уязвимым любой сервис на затронутой JVM.

Кого касается

Должны совпасть два условия.

Версия Java. OpenJDK 17.0.6 и новее, а также ветки 21, 25 и 27 до исправленных сборок (oss-security). У Oracle уязвимы Java SE 8u511b33-perf, 17.0.21.0.3, 21.0.13.0.3, 25.0.5.0.3 и 27.0.1.0.3, а также GraalVM for JDK 17 и 21 и GraalVM Enterprise 21.3.20.0.3 (запись CVE).

Процессор. x86-64 с поддержкой AVX-512 VBMI. По данным Calif, требованиям отвечают массовые семейства:

  • Intel Xeon: Ice Lake, Sapphire Rapids, Emerald Rapids, Granite Rapids;
  • AMD EPYC и Ryzen: Zen 4 и новее.

Calif пишет, что при первых тестах воспроизвела уязвимость без аутентификации в Keycloak, Jira, Confluence, Artifactory, Jenkins и PingFederate с настройками по умолчанию.

Насколько опасно

Оценки расходятся. Oracle даёт 8.1 по CVSS 3.1 с высокой сложностью атаки (AC:H), Calif — 9.2 по CVSS 4.0. На 17 ноября CISA по своей шкале SSVC оценила, что эксплуатации нет и автоматизировать атаку нельзя (запись CVE). На 21 ноября уязвимости нет в каталоге KEV (NVD). При этом 17 ноября Calif опубликовала самодостаточный PoC (oss-security), а цепочки атак для конкретных продуктов придержала.

Моя оценка: для Java-сервисов, доступных из интернета и работающих на x86-64 с AVX-512 VBMI, риск высокий, для всего на ARM64 и старых процессорах — низкий. Сложность атаки высокая, но PoC уже публичный, а сама ошибка, по таймлайну Calif, с июня была описана в открытом issue в Adoptium.

Почему это история про ИИ

По словам Calif, Quang Luong направил Codex на JIT, intrinsics и криптографию OpenJDK. Агент нашёл уязвимость за час, ещё два часа ушло на первый работающий эксплойт. Токены обошлись меньше чем в $200. Для меня это главное в истории: если поиск ошибки памяти в рантайме стоит час работы агента и пару сотен долларов, то атакующим он обходится так же дёшево. Значит, окно между выходом патча и первыми атаками будет только сокращаться.

Что сделать

  1. Проверьте, поддерживают ли процессоры x86-64 на ваших хостах AVX-512 VBMI. На Linux:
    grep -m1 -o avx512vbmi /proc/cpuinfo   # пусто — процессор не затронут
    В Kubernetes проверьте узлы, на которых запускаются Java-нагрузки.
  2. Найдите все JVM и их версии. Начните с интернет-сервисов: SSO, CI, трекеры, репозитории артефактов. java -version покажет только системную Java. У продуктов со своей JRE и в контейнерных образах версия может быть другой. Проверьте её прямо в запущенном процессе или в образе:
    jcmd <PID> VM.version                                   # версия JVM запущенного процесса
docker run --rm --entrypoint java <образ> -version      # версия Java в образе
  3. Обновитесь. Исправленные сборки OpenJDK — 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1 (на 21 ноября так их выпустили Ubuntu и Debian). Для Oracle Java SE — сборки из ноябрьского обновления Oracle. У Temurin, Corretto, Zulu и других смотрите бюллетень своего поставщика. CISA советует начинать с систем, доступных из интернета (алерт).
  4. Если обновиться сегодня нельзя, отключите соответствующие инструкции в рантайме Java флагом:
    JAVA_TOOL_OPTIONS="-XX:-UseBASE64Intrinsics"
    Второй вариант — -XX:UseAVX=2, только на x86-64 хостах. Он отключает AVX-512 в JVM целиком. Проверьте, что флаг применился:
    java -XX:+PrintFlagsFinal -version | grep UseBASE64Intrinsics   # должно быть false
    Это временная мера, патч она не заменяет.
  5. Следите за падениями JVM. Новые hs_err_pid*.log и неожиданные перезапуски Java-сервисов — повод разобраться. CISA отдельно советует искать неучтённые рантаймы и подозрительные Java-процессы.
